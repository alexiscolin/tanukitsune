# v0.1 spec

Single user. Levels 1 to 10. Ships when every acceptance criterion below passes.

Read `../framing.md` for why the architecture is shaped this way, `../backlog.md` for what was
considered and rejected, and `../workflow.md` for how work gets done.

## What ships

A WaniKani review client, in French, that works offline, running against the author's own account
with the token in an environment variable, plus a public demo anyone can try without an account.

It runs from a fresh clone with `pnpm bootstrap` then `pnpm dev`, and nothing else. `pnpm bootstrap`
installs and runs the migrations, and seeds the demo deck once the corpus terms are settled, which is
an open decision tracked in [`../decisions/`](../decisions/) rather than a missing step. The local database needs no starting: it is a
Postgres compiled to WebAssembly, opened as a directory in the working tree, so the rule that Postgres
is never mocked costs nothing to hold on a machine where nothing was installed beforehand. A token is
needed only to review a real account.

That contract is an acceptance criterion, not a convenience: a demo that takes a paragraph of
instructions to start is a demo nobody runs.

## The first slice is the toolchain

Before any feature: `package.json`, the scripts listed in `AGENTS.md`, the gates, and `pnpm bootstrap`.

`pnpm verify` is what every later claim of correctness rests on, and the `Stop` hook that enforces its
fast half exits silently when there is no `package.json`. Until that slice lands, the whole method described in
`workflow.md` is unenforced. It comes first, and the only behaviour it ships is `/api/health`, which
exists so the deployment identifier is readable and so the gates have something real to check.

## Out of scope, explicitly

No authentication, no multi-user, no token encryption, no subscription gating: the token lives in an
environment variable and only one person uses it. No LLM judge tier: tiers 1 and 2 decide or the user
self-grades. No FSRS: `review_events` is collected so that v0.2 can compute it, nothing more. No
themes, no stats, no notifications, no voice, no tutor, no MCP.

Anything not listed under "What ships" is out of scope, and adding it is a scope violation rather than
initiative.

## Data model

Three groups.

**Shared corpus**, identical for every user, generated once:
`corpus_entry(subject_id, locale, meaning, nuance, mnemonic, generated_by, prompt_version,
corpus_version, created_at)`. Keyed by subject and locale from the start, so a second language is not
a migration. `generated_by` carries the model ID and satisfies the AI Act transparency requirement.

**Cached in the browser**: subjects and assignments synced from WaniKani, and the corpus rows for the
locale in use. All three are caches of server truth, refetchable at any time, replaced wholesale and
never merged, so eviction costs a download rather than data. The corpus is held locally because the
item card has to appear on a wrong answer with no network, which is the moment the product exists.

**Ours, and irreplaceable**: `review_event(id, subject_id, locale, corpus_version, answered_at, kind,
answer, verdict, decided_by, correct, overridden_to, srs_stage_before, srs_stage_after,
applied_upstream, synced_at)`.
Append-only, client-generated UUID, never deleted, backed up server-side. WaniKani discards review
history, so this table is the only record that will ever exist.

`answer` is the answer as submitted, before the normalisation each tier applies for its own comparison.
A normalised answer freezes the rule that produced it, and on an append-only table that means a labelled
case can no longer be re-graded the day the rule changes, which is the same reason `locale` and
`corpus_version` are here. The judge cache is the opposite case and keeps its own obligation, in
[`../framing.md`](../framing.md) under obligations. `verdict` is what the cascade produced and
`overridden_to` is what the user said instead, null when there was no override: that pair is the
labelled disagreement every later eval rests on, and it cannot be reconstructed after the fact.
`decided_by` records which tier resolved the answer, which is what makes the v0.2 measurement possible.
`locale` and `corpus_version` record which reference the answer was graded against: the table is
append-only, so a verdict whose reference cannot be identified is a labelled case that can never be
replayed. `decided_by` carries the judge version while no model tier exists.
`srs_stage_after` and `applied_upstream` are null until the flush returns, because the stage exists
only in WaniKani's response and is never computed locally. Those two, plus `synced_at`, are the only
fields writable after the append.

## The review flow

Question, answer, verdict, next. The loop is the product, so it is the part that gets the design
attention and the latency budget.

**Input handling comes before everything else, and it is the first thing built.** This is a Japanese
typing app, so the answer field converts romaji to kana as it is typed and reviewing needs no Japanese
keyboard, per [ADR 0007](../decisions/0007-kana-input-in-the-field.md). A reader who keeps an input
method editor still composes, and Enter confirms that conversion before it submits anything. Without
gating on the composition state, Enter submits a half-typed answer on every review on mobile, which is
the characteristic bug of WaniKani clients. It would also make the judge's calibration meaningless,
because the judge would be grading truncated input rather than what the user meant. A reading still
holding anything but kana is refused with a message rather than graded, which is the same rule one step
later: a verdict on an unconverted answer grades something nobody typed. A dedicated input primitive,
with its own tests, before any other component.

**v0.1 ships no timer**, and that is the decision rather than a postponement. WCAG 2.2.1 is Level A, a
self-imposed review timer is not covered by the real-time exception, and retrofitting timer control is
a data model change rather than a styling one. The constraint governs from the moment one is added: a
timer that cannot be turned off, extended and adjusted does not ship.

On a wrong answer the item card appears immediately, showing the French meaning and mnemonic, the
readings, and the JLPT level, once a redistributable source for that mapping is named. That is the whole point of the corpus and it should be the moment the
product feels different from WaniKani.

Self-grade is available on every verdict, not only on failures. Every override writes a
`review_event` with the original verdict and the correction, because that override is a human
disagreeing with the grader on exactly the hard middle, and it is free labelled data that cannot be
recovered later.

## Corpus generation

A script, not part of the app. Reads the subject list for levels 1 to 10 and generates the French layer
through the batch API in one job. The item count comes from the API rather than from an estimate,
because the batch cost and the three-run budget are computed from it.

Idempotent and resumable, keyed by subject ID, written incrementally. A job that dies at 80 percent
must resume, not restart.

It publishes one chunk per locale and level, addressed by a hash of its content, plus a manifest
mapping each level to its current hash. Chunks are published before the manifest, never the reverse.

Mnemonics are generated from the primitives, the kanji, its readings and its meaning, never from
WaniKani's English mnemonics. That is both the legal position, since it avoids a derivative work, and
the better product, since a French sound association is not a translated English pun.

Quality gate is acceptance sampling, not regression: read a stratified sample by hand, and either ship
or revise the prompt and regenerate. Budget three full runs, because the first sample will be
mediocre. The prompt and its version live in git next to the code.

The rate being refused is two percent defective. A defect is any one of: a mnemonic that does not rest
on a French sound association, a meaning that is wrong, a nuance that contradicts the meaning, or an
entry that reads as translated from English rather than written in French.

The plan is n=150, c=1, stratified by item type and by level band: it accepts a two percent corpus
about three times in five and a five percent corpus about one time in five. A smaller plan does not
hold. n=60 with c=2 accepts a five percent corpus more often than it rejects it, which on a product
whose README says a wrong mnemonic teaches is not a gate. The rate, the sample size and the accept
number are written before the first run, because "ship or regenerate" is not a decision anyone can
take without all three.

Coverage is a separate gate from quality. Every subject in levels 1 to 10 has a row for `fr` before
ship. A vocabulary corpus contains entries that trip safety classifiers, so refusals are expected: a
refused item is written by hand and marked as such in `generated_by`. A missing row is treated by the
interface as a fetch failure, never rendered as an empty card, which is also its state during a
resumed run.

## The judge, tiers 1 and 2

**The tiers are scoped by answer kind, and this is the first thing to get right.** Every item is
reviewed for its meaning and for its reading, and the two are graded by different rules. A reading
answer is decided at tier 1 alone: exact match after normalisation, with small kana and dakuten treated
as distinct characters. Nothing fuzzy touches kana, where an edit distance of one accepts こうえん for
こうねん and converts a wrong reading into a correct one. Meaning answers go through both
tiers. The kind travels on `runCascade`'s existing input, so the frozen signature does not change when
the model tier arrives.

Tier 1 is exact match on normalised input: trim, Unicode NFKC, katakana folded to hiragana, lowercase.
**Only transformations that cannot make a wrong answer right belong here.** NFKC folds half-width kana
and full-width Latin onto their compatibility forms, and the katakana fold is a fixed offset over one
block, so both merge spellings of one answer rather than judging it. Neither is reversible, and that is
not what the criterion asks: what it asks is that no pair they merge is a pair of different answers. ミズ,
ﾐｽﾞ and みず are one reading, while こうえん stays refused for こうねん, きゆう for きゅう and か for が.
The prolonged sound mark is left alone, because コー and こう are not the same reading and the reference
is what says which one the item wants.

Tier 2 is fuzzy and applies to meaning answers only: accent folding, article tolerance, edit distance.
**French needs care here.** A generic edit distance accepts semantically opposite answers: `poisson`
and `poison`, `dessus` and `dessous`, `tache` and `tâche`, `sur` and `sûr`. A curated minimal-pair list
bypasses fuzzy matching entirely and requires an exact answer. Without it, tier 2 actively teaches the
wrong thing, which is worse than rejecting a correct answer.

That list is derived, not imagined. Run the tier 2 matcher over the French meanings for levels 1 to 10
at the configured edit distance, hand-review only the collisions it produces, and commit the result
with its count and the matcher configuration it was generated against. Regenerating it is a script, so
"the full set" is a checkable claim rather than a judgement.

Anything tier 2 cannot decide goes to self-grade with the item card shown. Never an automatic failure:
the product rule is that a correct answer is never punished, and in v0.1 the honest way to hold that
rule is to ask.

`core/grading` declares `JudgePort` and a pure `runCascade(input, port)` even though no
implementation exists yet, so v0.1.1 adds the LLM tier without changing what the cascade is called with.
The stages themselves grow, since tier 2 is inserted between the exact tier and the judge. It does extend
what the port receives, which today carries only what a decision needs: the cache key in
[`../ai-engineering.md`](../ai-engineering.md) also needs the item, the locale and the corpus version,
and it keys on the normalised answer, so the tier that caches is handed those and imports the
normaliser rather than writing a second one. Without that, the cache cannot hold its own obligation and
an override has no key to point-delete.

## Offline and sync

The review queue is an append-only log of answers with client-generated IDs, not a mutable list. Sync
replays the log, and replaying it twice must be safe.

**The flush unit is the subject, not the answer.** WaniKani advances an item only when both its meaning
and its reading have been answered, so a partial subject is held in the outbox until its pair arrives
rather than submitted alone and corrected later.

An uncertain failure is resolved by re-reading the assignment state, never by resubmitting blind, and a
422 means drop and resync rather than retry. Server state wins on conflict. Storage eviction is handled
explicitly: request persistence, read the result, and warn when it is refused. The reasoning behind all
three is in [`../framing.md`](../framing.md) under offline reconciliation.

Multi-tab is a real case in week one, not an edge case: two tabs share IndexedDB and would otherwise
run two queues. A single sync leader, elected through the Web Locks API.

## Demo mode

A seeded deck of about twenty items, no token, running the real review flow, the real corpus and the
real cascade against local state. No writes means nothing leaves the device: answers still append to
the local outbox, because that write is part of the flow being demonstrated, but nothing is submitted
upstream and nothing is backed up to the server. The outbox is cleared when the deck is restarted. Reachable from the top of the README.

This is the artifact the project ranks highest, so it is a v0.1 deliverable rather than a polish item.

## Acceptance criteria

- A review session of thirty items completes offline, with airplane mode on, and syncs correctly on
  reconnect
- The same session run twice from the same queue produces one set of submissions, not two
- Enter during an active composition confirms the conversion and does not submit, verified on iOS
  Safari and Android Chrome rather than only in a desktop emulator
- A reading typed on a keyboard with no Japanese layout reaches the field as kana, and one still holding
  romaji is refused with a message rather than graded
- A queue built in the browser is not lost when the app is installed to the home screen
- A wrong answer shows the French item card in under 100ms at the 95th percentile, measured from the
  verdict being decided to the card being painted, with a performance mark at each end and the
  measurement read in the end-to-end suite
- `review_events` contains one durable row per answer, with the tier that decided it
- The minimal-pair list rejects `poison` for 魚 and accepts an unaccented `tache` only where the item
  allows it
- Demo mode works in a fresh browser with no configuration
- A fresh clone reaches that demo with `pnpm bootstrap` then `pnpm dev`, on a machine that has only Node
  and pnpm, with no step performed by hand
- The demo is reachable at a stable public URL by someone with no clone, no token and no account, and
  that URL is the first link in the README
- A reading answer is never resolved by fuzzy matching: こうえん is rejected for こうねん, and small
  kana and dakuten differences are rejected
- The cascade is measured on a committed answer set, not asserted. Fall-through to self-grade stays
  under fifteen percent of that set, which is a diagnostic budget rather than a production rate: the
  set is hand-built and cannot carry one. The representative rate turns on with the eval set, whose
  sampling frame is in `../ai-engineering.md`, and its threshold is fixed the first time that set
  exists rather than now, because a number chosen before the data is a number chosen without it. False
  accepts on the minimal-pair set are zero, and false rejects are reported as their own number rather
  than folded into an accuracy figure
- Corpus generation resumes correctly after being killed halfway
- No route on the public deployment reads the WaniKani token, and the flush and backup routes reject a
  request without the shared secret
- `pnpm verify` passes: types, lint, boundaries, tests, dead code, duplication
- Every generated item displays its provenance

## Verification

End to end with Playwright for the offline path, the sync path and the demo, because those cannot be
unit tested. Everything in `core/` unit tested exhaustively, including the generated minimal-pair set.
Postgres real, never mocked. The WaniKani API mocked at the HTTP boundary only.

Accessibility is audited by axe inside that same Playwright run, on the rendered page rather than on
the source, and a violation fails the suite. That is the accessibility gate: there is no lint rule for
it, because the plugin that would provide one does not support the linter this project uses.

The end-to-end suite runs against the production build, not the development server, because the offline
paths it exists to cover behave differently under the latter. In CI it runs against a server Postgres
rather than the local file-backed one, so the driver that runs in production is the driver a merge is
gated on.

The grading gate runs in Vitest, because `runCascade` is pure: a committed set of answers with expected
outcomes produces the fall-through, false-accept and false-reject numbers on every run. That set is
also the seed of the calibration set the model tier will need, so it is built once and reused.

Composition handling is verified twice, because no automated driver produces a real conversion. The
input primitive is unit tested against synthetic composition events in CI, which is the commit that
adds jsdom and the component test setup since `core/` needs neither, and a manual pass on one
physical iPhone and one physical Android device runs before each release, dated in `../agent-log.md`
with the devices and the operating system versions. The manual gate is the mechanism, not an admission
that one is missing.
